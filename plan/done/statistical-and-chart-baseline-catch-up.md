## What the CI logs can and cannot give

The CI logs are a control and a first hint. The CI logs are not the measurement, for three reasons.

1. **A red test hides its later changes.** A test that fails stays red until its baseline changes. The log shows the first failure only. F12 shows that later changes of the same file are frequent.
2. **Each run used moving inputs** (F7). A failure can come from OMNeT++, from the tool, or from a baseline commit, and not from the INET push.
3. **A push is not a commit.** 88 push ranges hold more than one relevant commit (F4).

Thus the measurement is a local run in a copy of the GitHub job on this machine, with one fixed environment, against the chain of this plan. The walk does not wait for GitHub CI. The CI runs give the push heads for the probes, and a CI log can help with an explanation.

- **Environment**: one fixed set for the complete walk (decision D6): the job container on this machine (the Ubuntu 24.04 image, clang 16), the head of `omnetpp-6.x` and the head of `opp_repl@github_ci` on the day of step A2, and the Python packages of that day. The test command is the command in the workflow file of the INET commit. Thus an INET commit before the change to opp_repl (2026-10-27) uses the Python tools in its own tree.
- **Chain**: the branch `topic/baseline-catch-up` in `statistics` and in `media`. The chain starts at the baseline commits of G. The two branches move together: each position of the walk has one commit of `statistics` and one commit of `media`.
- **Position**: the INET commit up to which the walk is complete. At the position, the two complete tests pass against the chain, or have an expected result.
- **Probe**: a run of the two complete tests at a later INET commit against the chain. A probe finds the next failure.
- **Step**: one cause and all the statistical tests and chart tests that the cause moves. A cause is one INET commit, or the smallest part of one commit, or one environment change.
- **Candidate**: a result file or a chart image that a run made. A candidate is evidence. A candidate becomes a baseline only in a step, after approval.

## Design

The walk starts at G and goes forward one step at a time. The walk carries the two baselines together. Each probe and each step runs the two tests, because a chart can show a change that the statistical baseline does not hold. For example, a vector can change much while its mean changes little. A chart also draws all the runs of a parameter study, while the statistical test reads run 0 only.

No pass over all push heads comes first. Step 1 is ready after the first probes. The first steps can then correct the procedure before the walk uses much machine time.

### Phase A: setup

1. Archive the job logs of the 362 runs (the green run and the 180 pushes, two workflows), because GitHub removes old logs after a retention time. The logs are a help for the explanations. The walk does not depend on them.
2. Make a new job copy, `~/workspace/ghci-baseline-catch-up`, from the recipe of `ghci-statistical/tools`. The copy has its own worktrees of `omnetpp`, `inet`, `statistics` and `media`. The old copy stays with its task (F10).
3. Reproduce G: with the environment and the chain at its start, the two complete tests give the summary of F1. This result is the gate for the walk. If a test fails here, the cause is the environment, because the green run used OMNeT++ 6.4.0 and the tools of that day. A second run at G with OMNeT++ `820d04e7bb` proves this cause. The difference then becomes step 0, with the verdict `environment`.

### Phase B: the walk

The walk repeats the loop below. The position P is G at the start.

1. **Probe.** Take the next push head H after P whose range from P holds a relevant commit (F3). Build H. Run the two complete tests against the chain, with all cores of the machine.
2. **No failure.** P becomes H. Go to item 1.
3. **Failure.** Find the first commit with a bisect over the relevant commits between P and H (decision D9). The test of the bisect is: one of the failed tests fails against the chain. The first commit that fails is C. If the range holds more than one cause, the bisect finds the earliest cause, and the next probe of H finds the next one.
4. **Scope.** Run the two complete tests at C against the chain. The tests that fail at C are the scope of the step. Each of them must pass at the parent of C (F14). A test that fails at the parent too has an earlier cause, and the search goes back for that test.
5. **Step.** Do the procedure of one step. After the approval, the chain gets the commit of the step: in `statistics`, in `media`, or in the two.
6. P becomes C. Go to item 1. The next probe is H again, because H can hold more failures.

While a step waits for its approval, the machine can go on with the loop on a copy of the chain that holds the candidates of the open step (decision D8). This work prepares the next step. Nothing goes to the chain before the approval. If the user changes an open step, the prepared work after that step is done again.

The earlier knowledge is input to the explanations, not proof: the 25 commit messages of `statistics` (F8), the earlier review (F11), and the attributions in the notes of 2026-10-27. Each explanation is checked against the runs of the walk, which come from the CI environment.

Estimate, not measured: a probe needs an incremental build and the time of the two tests. In the old job copy, the statistical test needed 6 minutes with 12 workers. The chart job on GitHub needs 27 to 48 minutes with 4 cores. Step A3 gives the local times with all 30 cores. An earlier run with 32 workers was stopped by systemd-oomd; if that occurs again, the number of workers goes down. The walk needs at most 139 probes at push heads and about one more probe for each step. Each step also needs a bisect of at most 6 builds with a small set of tests, because the largest range holds 38 relevant commits.

### Phase C: end check and landing

1. The walk ends when P is the head of `master` of that day. The last probe is the complete end check. Then run the two complete tests one more time with the heads of `omnetpp-6.x` and `opp_repl@github_ci` of that day. After the landing, the GitHub CI run of `master` is the last proof.
2. Cross-check with `master` of `statistics` and `media`: for each test that passes at M today, the file on the chain must be equal to the file on `master`. Each difference needs an explanation.
3. Land the chain. The method is decision D5, at that time. The branches stay local until the user asks for a push.

## Procedure of one step

1. **Scope.** Take the scope from item 4 of the loop: the statistical tests with their row counts (added, removed, changed), and the charts with their metric.
2. **Smallest cause.** Read the diff of the commit. If the commit holds more than one behavior change, or the rows and charts do not follow from the diff, do a split experiment in a scratch build: find the smallest patch that reproduces all the moved rows and charts, and check that its reverse restores the parent results.
3. **Explanation.** Write why the code change is correct: a clause of a standard, a repaired defect, a deliberate model change. Then account for each group of moved rows as a result of that change (F13). For each moved chart, say how the picture changes and why. Record the vectors of each moved test at the parent and at the commit with `tools/vectors.sh <step>` (from step 58 on; decision D2 of the omnet-julia plan `the-ide-follows-the-baseline-catch-up.md`): the step page shows, for each vector, the first sample that differs. Delete the `.vec` and `.vci` files after the approval of the step; the `.sca` files stay.
4. **Verdict.** One of:
   - `correct`: a repair or a deliberate model change with a basis;
   - `neutral`: no change of model behavior, for example new or renamed result rows, or a change of the test setup;
   - `environment`: OMNeT++, tool, or package version. Only step 0 can have this verdict, because the environment is fixed;
   - `defect`: the change, or a side effect of the change, is wrong;
   - `unexplained`: a row group or a chart has no explanation. The step stops. No baseline changes until the cause is known.
5. **Approval** by the user, for each step alone (decision D4). The request shows the scope, the cause, the explanation and the verdict. For each moved chart, the request shows the old image, the new image and the difference image. No baseline changes before the approval.
6. **Commit** the candidates of the step to the chain. The message gives the explanation and ends with the trailer `INET-Commit: <sha>`. An environment step names the OMNeT++ or tool commit instead. A `defect` step has the trailer `Defect: BD-<n>` too.
7. **Record** the step in the ledger, and the defect in the defect list. Put an annotated tag `catch-up/step-<n>` on the INET commit of the step, with the verdict in its first line (user, 2026-11-12: the points must be easy to find in gitk). The tags are local; do not push them. Write `meta.json` of the step (commit, verdict, state, cause, notes, charts, the list `experiments`: for each experiment its name, its patch file, what it tests and its result, decision D9 of the omnet-julia plan; and `diff`, the smallest diff of the source that gives the result, which the step page and the summary show as a code block, user 2026-11-18) and run `tools/summarize.sh`, which writes the summary page of the step and the index. `tools/progress.sh` writes the pages of the IDE (see Records) after each approved step.
8. **Check.** Run the moved tests at C against the new chain. The tests must pass. The next probe is the complete check.

A new test gets its first baseline at the commit that adds the test. That step has no parent values, so the explanation is a check that the results are plausible. A removed test loses its baseline file at the commit that removes the test.

## Limits

- A test that moves and moves back between two probes is not visible. Such a pair changes no baseline.
- A chart can move below the limit of the metric. The chart test then passes, and the image stays.
- All runs are in the job container on this machine (Ubuntu 24.04, clang 16, glibc 2.39, the z3 of that image), not with the compiler of the host. Reason: error-rate values and the z3 schedule of `gsandcs` differ with the compiler and the libraries of the host, and such baselines fail in GitHub CI. The same is true for the runners of GitHub: when `ubuntu-latest` became Ubuntu 26.04 (clang 21, z3 4.13.3), 12 baselines moved (C2). Since 2026-11-23 the job container is `localhost/ghci-statistical:26.04-clang21`, the environment of those runners.
- The bisect expects that a test which fails at H fails from its first bad commit to H. If a test fails, passes and fails again in one range, the bisect can find the later cause first. Item 4 of the loop then shows that the test fails at the parent, and the search goes back.
- The walk does not compare each probe with the CI log. The environment is not that of the old CI runs, so the two results can differ for a reason that is not INET.
- A split experiment gives a smallest patch that is sufficient. The experiment does not prove that no smaller patch exists.
- In a push range with several causes (the TCP defaults, steps 41 to 52), each bisect starts at the last step commit and uses the list of the failing end probe, without a new probe of the end. When no test point fails, the result is the untested end: `tools/bisect.sh` then prints a NOTE, and a full probe of the end decides.
