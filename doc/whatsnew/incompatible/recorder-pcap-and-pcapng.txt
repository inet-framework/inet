PCAP and PCAPng: Radiotap records, the PCAPng block API, and correct records

A PcapRecorder with the helper inet::physicallayer::Ieee80211RadiotapPcapRecorderHelper writes IEEE 802.11 frames as Radiotap records (link type 127), the format of Linux monitor mode. Wireshark then shows the data rate or the HT or VHT MCS, the channel frequency, the transmit power of a sent frame, and the signal power, the noise and the start time of a received frame. A frame that the receiver could not decode has the "bad FCS" flag. The noise is the signal power divided by the minimum SNIR, so it includes the interference. Without the helper, the records stay plain 802.11 records (link type 105). The PCAP recording showcase has a Radiotap configuration:

  *.host1.pcapRecorder[0].helpers = "inet::physicallayer::Ieee80211RadiotapPcapRecorderHelper"

For this, PcapRecorder asks its helpers before its own table of link types, and PcapRecorder::IHelper::tryConvertToLinkType() has the new last parameter Direction direction. A helper outside INET must add the parameter. PcapRecorder now also writes the copy of the frame that the receiver got, which the radio gives with the receptionEnded signal, with its bit error and its tags; before, it wrote the packet of the transmitter, so a frame that the receiver could not decode looked good in the file, and dumpBadFrames = false did not remove it.

PcapngWriter has public functions for the blocks of the format, writeSectionHeaderBlock(), writeInterfaceDescriptionBlock() and writeEnhancedPacketBlock(), with the typed options PcapngSectionOptions, PcapngInterfaceOptions and PcapngPacketOptions, and addOption() for any other option. A caller can mix these functions with writePacket() in one file, and a packet with an undefined direction gets no epb_flags option instead of an error. It sets the CRC error flag of each packet with a bit error, for each link type, so Wireshark shows "CRC error"; PcapRecorder keeps such frames when dumpBadFrames is true, which is the default. It truncates records at a finite snaplen limit but keeps their original lengths; before, it wrote complete records. Set a large limit, or zero, which is unlimited, if your tools need complete records. Each link type of an interface now has its own interface description, so a reader no longer decodes a packet with the link type of another packet. A packet without a network interface, for example from PacketFlowPcapFileRecorder or PcapFilePacketConsumer, no longer crashes the writer: it refers to an interface description without a name and addresses.

PcapReader, which PcapFilePacketProducer uses, now reads Radiotap captures, IEEE 802.15.4 captures (link types 195 and 230) and captures of bare IP packets (link types 101, 228 and 229). The new tag FcsInd tells whether the frame has an FCS. The reader no longer depends on uninitialized memory for the link type, and a short read at the end of a file no longer throws.

See the migration guide for the helper direction and the capture limits.

The Radiotap capture and the PCAPng corrections are based on pull request #1130 of Miguel González-López.
