IEEE 802.1ad: S-tags and C-tags together, port-based VLAN policy, and the PCP of the tag inserters

A node can now carry the VLAN id, the PCP and the drop eligible indicator of an S-tag (IEEE 802.1ad) and of a C-tag at the same time, so it can insert or remove both tags, as a provider edge bridge or the UPF of a 3GPP Ethernet PDU session does. The request and indication tags of the C-tag therefore have the C-tag in their names, and the S-tag has tags of its own. There are no aliases: code that attaches or reads these tags, and a classifierClass parameter that names an old classifier function, must use the new names:

  VlanReq, VlanInd                    -> CVlanReq, CVlanInd           (new for the S-tag: SVlanReq, SVlanInd)
  PcpReq, PcpInd                      -> CPcpReq, CPcpInd             (new for the S-tag: SPcpReq, SPcpInd)
  DropEligibleReq, DropEligibleInd    -> CDropEligibleReq, CDropEligibleInd   (new: SDropEligibleReq, SDropEligibleInd)
  inet::PacketVlanReqClassifier       -> inet::PacketCVlanReqClassifier   (new: inet::PacketSVlanReqClassifier)
  inet::PacketVlanIndClassifier       -> inet::PacketCVlanIndClassifier   (new: inet::PacketSVlanIndClassifier)

The modules that use the VLAN tags have a vlanTagType parameter, "c" by default: the VLAN policy modules, the relays with their learners and selectors, Ieee8021qSocketPacketProcessor, PcpClassifier, PcpTrafficClassClassifier, GroupEligibilityTimeMeter, StreamEncoder, StreamDecoder and the packet taggers. Ieee8021qLayer, VlanPolicyLayer, BridgingLayer, InterfaceRelayLayer and StreamCoderLayer pass theirs to their submodules, so one line makes a whole node an S-VLAN bridge: *.switch.**.vlanTagType = "s". An 802.1Q tag inserter or checker with vlanTagType "s" reads and writes only the tags of the S-tag. An S-VLAN node must set vlanTagType on all of these modules: a node that sets it only on the 802.1Q layer, which was enough before, runs without VLAN separation or stops with an error that does not name the cause. The protocol parameter of VlanReqMapper is replaced by vlanTagType; delete the lines that set it. PacketDirectionReverser and the MAC relays turn the indications of both tags into requests, so a bridge that decodes both tags keeps both when it forwards a frame. The packet printer shows a tag as "S-tag pcp = 2, dei = false, vid = 81" or "C-tag pcp = 0, dei = false, vid = 42".

An 802.1Q tag inserter (Ieee8021qTagEpdHeaderInserter, Ieee8021qTagTpidHeaderInserter) now takes the PCP of its tag in three steps. First, it maps a user priority request to a PCP request of its tag type, unless the packet has one (mapUserPriorityReqToPcpReq, true by default); it removes the user priority request only if removeUserPriorityReq is true, and the default false leaves the request for the layers below, as IEEE Std 802.1Q-2018 6.9.2 requires. Second, it takes the PCP from the PCP request, or from defaultPcp. Third, it indicates the PCP of its tag as the user priority of the frame (mapPcpIndToUserPriorityInd, true by default). In a node that inserts a C-tag and an S-tag, the S-tag inserter runs last, so its PCP is indicated, unless its mapPcpIndToUserPriorityInd is false. Before, defaultPcp overrode an explicit user priority request, and a PCP that came from the user priority was not indicated as a PCP. A PCP request, a used user priority request or a defaultPcp outside [0, 7] is an error now, and so is removeUserPriorityReq without mapUserPriorityReqToPcpReq. The defaultUserPriority parameter is removed; defaultPcp takes its place and gives the frame the same user priority indication:

  **.qTagHeaderInserter.defaultUserPriority = 5  ->  **.qTagHeaderInserter.defaultPcp = 5

The lookup and update methods of IMacForwardingTable, MacForwardingTable and MrpMacForwardingTable no longer have a default VLAN ID of 0, which let the classic relays look up tagged frames in the wrong VLAN. Code outside INET that calls them without a VLAN ID does not compile: give the VLAN of the frame, or 0 if the caller does not know VLANs.

Ieee8021adPolicy is a new VLAN policy for the vlanPolicy submodule of BridgingLayer. Its ports parameter gives the IEEE 802.1Q port type and the VLAN ids of each port of the bridge: "access" and "trunk" for a C-VLAN bridge, "cnp" (Customer Network Port) and "pnp" (Provider Network Port) for an S-VLAN bridge of a provider network. One line replaces the four maps of each port of VlanPolicyLayer, and the module follows the rules of IEEE 802.1Q-2018 for these ports: an access port also accepts priority-tagged frames, and a frame sent untagged leaves without a priority tag, so the bridges need no forwardPcp = false. Invalid ports, a port type that does not agree with vlanTagType, and a port of the relay without an entry are errors at initialization, and the module forgets the port of a deleted interface. A module that creates network interfaces during the run sets a port with setPort() and removes it with removePort(). For example:

  *.switch.bridging.vlanPolicy.typename = "Ieee8021adPolicy"
  *.switch.bridging.vlanPolicy.ports = {"eth0" : {"type" : "access", "vid" : 10}, "eth1" : {"type" : "trunk", "vids" : [10, 20]}}

VlanPolicyLayer stays for VLAN id translation, hosts and other configurations. Its new VlanIndMapper module maps the VLAN id of a received frame for each incoming interface (-1 for untagged, 0 for priority-tagged), so two untagged ports of one bridge can be in different VLANs. VlanReqMapper, VlanReqFilter and VlanIndFilter check their maps at initialization, and they have setter methods for ports that are created during the run. The new example examples/ethernet/providerbridging and the new showcase showcases/ethernet/sharedcore show provider bridging. See the migration guide.
