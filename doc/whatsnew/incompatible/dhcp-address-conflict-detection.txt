DHCP checks the granted address, and follows RFC 2131 more closely

A DHCP client now checks that the address that it was granted is not in use, as RFC 2131 section 4.4.1 asks, with an ARP Probe of RFC 5227 section 2.1.1. It sends the probe after REQUESTING or REBOOTING on a link that uses ARP, and it waits probeWait (1s by default; 0s turns the check off). It takes the address only if nobody answers. If somebody answers, it sends a DHCPDECLINE and starts again. DhcpServer marks a declined address unavailable, as RFC 2131 section 4.3.3 requires; before, the server offered the same address again for the whole run.

DhcpClient has the new parameters arpModule and probeWait, and Arp has the new signal arpAddressConflictDetected. IArp has the new pure virtual method sendArpProbe(), so an IArp implementation outside INET must override it; GlobalArp overrides it with an empty body. Arp now also accepts a probe from a neighbour: before, a probe, which has an all-zero sender protocol address, stopped the run with "wrong ARP packet: source IPv4 address is empty". See the migration guide.

The client and the server also correct seven defects. The client keeps the transaction identifier of the exchange in its DHCPREQUEST, and it repeats a DHCPREQUEST with the randomized exponential backoff of RFC 2131 section 4.1 (4 seconds that double up to 64) in the initial exchange; before, it waited a constant 60 seconds and did not repeat a request. The server copies the giaddr of the DHCPDISCOVER into its DHCPOFFER, writes no leased address into the ciaddr of a DHCPACK, copies the flags of the message that it answers, sends no domain name server option of 0.0.0.0, and answers a DHCPREQUEST for an address of a foreign subnet with a DHCPNAK. A DHCPDECLINE carries the server identifier, which RFC 2131 table 5 requires.

Each DHCP client now waits probeWait between the acknowledgement and the use of the address, so the traffic of the client starts one probeWait later; the lease timers T1 and T2 do not move. DHCP exchanges take different times and put different bytes on the wire, so the trajectories and the fingerprints of simulations that use DHCP change.
