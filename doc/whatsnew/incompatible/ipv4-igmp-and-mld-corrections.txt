IGMP and MLD corrections

An IGMPv3 Query now carries the QRV and the QQIC of its querier: the Robustness Variable (0 above 7) and the code of the Query Interval (RFC 9776 sections 4.1.6 and 4.1.7). Before, both fields were 0. An MLDv2 Query now carries them too (RFC 9777 sections 5.1.8 and 5.1.9).

An IGMPv3 Report and Leave, also the IGMPv2 messages of a host in IGMPv2 mode, now leave with the precedence of Internetwork Control, Type of Service 0xc0 (RFC 9776 section 4), as the Queries already did.

Every MLD message, of Mldv1 and of Mldv2, now leaves from the link-local address of its interface (RFC 2710 section 3, RFC 9777 section 5), once Duplicate Address Detection has tested it. Before, it left from the global address. So the querier of an interface now starts when the interface has a tested link-local address, up to about 2 seconds after the start, and a Report or a Done waits until then. Ipv6InterfaceData now emits the interfaceIpv6ConfigChanged signal when an address becomes tentative or valid.

The Ipv6 module now counts the extension headers that a sender asks for with an Ipv6ExtHeaderReq tag in the Payload Length of the datagram (RFC 8200 section 3). Before, the Payload Length counted only the upper-layer message, so the receiver cut off the end of the message.

Every MLD message, of Mldv1 and of Mldv2, now carries the Router Alert option of RFC 2711 in a Hop-by-Hop Options header (RFC 2710 section 3, RFC 9777 section 5). The new Ipv6RouterAlertOption class holds the option, and the serializer reads and writes it. A multicast router now delivers a multicast datagram locally when the datagram carries the option. Before, it delivered every ICMPv6 multicast datagram locally, to receive the MLD messages.

In the "computed" checksum mode, the checksum of every ICMPv6 message now covers the pseudo-header of the IPv6 datagram (RFC 4443 section 2.3): MLD, Neighbor Discovery, Echo and the error messages. The Ipv6 module computes it when the source address is final, with the new Icmpv6::insertComputedChecksum(), and Icmpv6 checks it with the addresses of the datagram. Before, the checksum covered the message only, so a real node or a capture tool rejected every message. The "declared" mode, the default, does not change.

An Mldv1 node now ignores an MLDv2 Report (RFC 4443 section 2.4). Before, the simulation stopped with an error when an MLDv2 host sent a Report on a link with an Mldv1 router before it heard the first MLDv1 Query.

An IPv6 interface now joins the solicited-node multicast group of each of its unicast addresses when it gets the address, before Duplicate Address Detection, and leaves it with the last address of that group (RFC 4861 section 7.2.1, RFC 4862 section 5.4.2). Before, a node only accepted packets to these groups, and MLD never reported them. With MLD on, a node now sends Reports for its solicited-node groups, and the group lists of an interface hold them.

Two defaults of Igmpv3 now have the values of RFC 9776 (sections 8.11 and 8.4): unsolicitedReportInterval is 1 s, before 10 s, and groupMembershipInterval adds twice the Query Response Interval, 270 s with the other defaults, before 260 s. The timer of a router for an older host used groupMembershipInterval; it now has its own parameter, olderHostPresentInterval, which keeps the value of RFC 9776 section 8.13, 260 s with the defaults.

The same two defaults of Mldv2 now have the values of RFC 9777 (sections 9.11 and 9.4): unsolicitedReportInterval is 1 s, before 10 s, and groupMembershipInterval, the Multicast Address Listening Interval, adds twice the Query Response Interval, 270 s with the other defaults, before 260 s. The new olderVersionHostPresentInterval keeps the value of RFC 9777 section 9.13 for the timer of a router for an MLDv1 host, 260 s with the defaults.

The IGMPv2 or IGMPv1 mode of an Igmpv3 host now lasts for the Older Version Querier Present Interval of RFC 9776 section 8.12: [Robustness Variable] x [Query Interval] + 10 x the Max Response Time of the last older-version Query, 350 s with the defaults. Before, it lasted for otherQuerierPresentInterval, 255 s, the interval of the querier election.

The MLDv1 mode of an Mldv2 node now lasts for the Older Version Querier Present Interval of RFC 9777 section 9.12: [Robustness Variable] x [Query Interval] + [Query Response Interval], 260 s with the defaults. Before, it lasted for otherQuerierPresentInterval, 255 s.

An Igmpv3 host that changes the state of a group again before the repetitions of its State-Change Report end now merges the pending records, as RFC 9776 section 5.1 asks: each source of a change stays in the next [Robustness Variable] State-Change Reports, and a filter-mode change stays in them as a TO_IN or TO_EX record. Before, the second change replaced the pending records, so a source of the first change could leave fewer times.

An Mldv2 node merges the pending records in the same way (RFC 9777 section 6.1).

The IGMPv1 and IGMPv2 modes of an Igmpv3 host now follow the host state machine of RFC 2236 section 6: a Query starts a report delay timer with a random value up to its Max Response Time, the Report of another member stops the timer, a join repeats its Report after up to unsolicitedReportInterval, and a Leave goes out only from the host that sent the last Report. Before, every member answered at the instant of the Query and sent one Report for a join.

The MLDv1 mode of an Mldv2 node follows the node state machine of RFC 2710 section 5 in the same way, with the Maximum Response Delay of the MLDv1 Query and a Done only from the node that sent the last Report.

A change of the compatibility mode of an Igmpv3 host now cancels all its pending response and retransmission timers on the interface (RFC 9776 section 7.2.1). Before, an IGMPv3 host that entered the IGMPv2 mode still sent the pending repetitions of its IGMPv3 State-Change Report.

A change of the compatibility mode of an Mldv2 node cancels its pending timers in the same way (RFC 9777 section 8.2.1), and deletes the Reports of the old mode that wait for the link-local address of the interface.

An Igmpv3 host now leaves out of its answers to Queries a group that it has left, and sends no record with an empty set of sources (RFC 9776 section 5.2). Before, it answered every General Query with a MODE_IS_INCLUDE record with no sources for each group that it had left, and a source-specific Query for sources that it did not want with such a record too.

An Mldv2 node leaves such records out in the same way (RFC 9777 section 6.3).

The S flag (Suppress Router-Side Processing) of a Group-Specific Query of Igmpv3 now comes from the group timer after it is lowered to the Last Member Query Time (RFC 9776 section 6.6.3.1), for the first Query and for each retransmission. Before, the first Query took the flag from the timer before it was lowered, so the flag was set after the leave of the only member, and every retransmission had the flag set.

The S flag of a Multicast Address Specific Query of Mldv2 comes from the lowered Filter Timer in the same way (RFC 9777 section 7.6.3.1).

The Group-Specific and Group-and-Source-Specific Queries of Igmpv3 now keep the retransmission state of RFC 9776 section 6.6.3. A Report no longer ends the retransmissions of the Queries; it changes only the timers. A Group-and-Source-Specific Query lowers the Source Timers of its sources to the Last Member Query Time, and each transmission is two Queries: one with the S flag for the sources whose timer is larger than that time, and one without it for the others. Before, a source that the last member blocked stayed forwarded until its Source Timer ended, up to 260 s later.

The Multicast Address Specific and Multicast Address and Source Specific Queries of Mldv2 keep the same state (RFC 9777 section 7.6.3).

IPv4 now forwards a multicast datagram onto a leaf interface only when the interface has a listener of its source, as the IGMPv3 state of the router says (RFC 9776 section 6.3). Before, a listener of the group was enough, so the source lists of IGMPv3 had no effect on the data. Ipv4InterfaceData::hasMulticastListener(group, source) also returned the opposite answer; it is corrected.

IPv6 forwards a multicast datagram onto a leaf interface only when the interface has a listener of its source in the same way (RFC 9777 section 7.3).

An Mldv1 node now accepts an MLDv2 Query and reads its first 24 octets as an MLDv1 Query (RFC 2710 section 5, RFC 9777 section 8.1). Before, the simulation stopped with an error when an Mldv1 node received a Query from an Mldv2 querier.
