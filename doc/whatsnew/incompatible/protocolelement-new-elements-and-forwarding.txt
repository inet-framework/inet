Protocol elements: new elements, a Forwarding with routes, and many repairs

The protocol element library has new elements: SendFromL3Address and ReceiveFromL3Address, SendFromPort and ReceiveFromPort, SendFromMacAddress and ReceiveFromMacAddress, which put the source into a header and into an indication tag; NextHopMacResolver, with a static table of neighbors; SendWithLifetime and ReceiveWithLifetime, which drop packets older than maxLifetime; ExponentialBackoff; and SimplifiedRadioMedium, with ranges and a packet loss probability. Resending stamps the new TransmissionAttemptReq tag with its retry counter. The new example examples/protocolelement/reliablemesh builds a reliable multi-hop wireless transfer only from protocol elements.

Forwarding no longer has a fixed next-hop table. Its new parameters address, routes ("destination nextHop [interface]" entries, separated by ";") and interfaceTableModule give the routes, and it requests the next hop and the interface with NextHopAddressReq and InterfaceReq. It no longer makes a destination MAC address from the next-hop address, and it drops a packet without a route with NO_ROUTE_FOUND; before, it delivered such a packet locally. A chain that used the old behavior needs NextHopMacResolver.

Many elements could not run before. Thirteen elements, for example SendWithAcknowledge, ReceiveWithProtocol and SendToMacAddress, could not be created ("Unknown parameter backpressure"). Some also had defects: ReceiveWithHopLimit removed its header twice, SendWithHopLimit added it twice, ReceiveWithProtocol consumed each packet, SendWithAcknowledge sent the data twice and took acknowledgements for timeouts, and SendToMacAddress called itself without end. These elements now work.

The canPushPacket() method of Resending tested its packet argument instead of the packet that the module holds, so it refused each packet that a producer asked about. An active producer that asks before it pushes, for example a PacketServer after a queue, therefore never passed a packet to Resending. Resending now accepts a packet whenever it holds none. The client of the steps Network6 and Network7 of tutorials/protocol now sends its packet.

PacketReceiverBase, the base of PacketReceiver, DestreamingReceiver and StreamThroughReceiver, wrote the bit error flag of the received signal over the flag of the packet. A packet with its own bit error, in a signal without one, thus lost its bit error. Now the signal can only add a bit error to the packet; for example, the FCS checker of LayeredEthernetInterface discards such a frame.
