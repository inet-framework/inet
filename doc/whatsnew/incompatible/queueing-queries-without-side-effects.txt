Queueing: a query does not change the state of a module, and a sink can pull the packet that it accepts

IPassivePacketSource has the new methods canPullPacket(gate, filter) and pullPacket(gate, filter). The filter, an IPacketFilterFunction, is the acceptance condition of the sink, and the source answers as if it held only the packets that the filter matches. This is the pull form of canPushPacket(packet, gate): a sink can now take a packet behind a packet that it cannot accept. PassivePacketSource, EmptyPacketSource, PacketQueue, PriorityScheduler, WrrScheduler and the compound queues support the filter, and IPacketQueue has the new method dequeuePacket(filter). CPacketFilterFunction accepts a callable with captured values, so a consumer can give its current condition. The base classes throw an error for a filtered call that a module cannot answer. Simulation results do not change.

A query, for example canPushPacket() or canPullPacket(), no longer changes the state of a module. PacketClassifierBase::classifyPacket() and PacketSchedulerBase::schedulePacket() are const functions, because the base classes call them from queries and again from the operation that moves the packet. The base classes call the new functions handlePacketClassified(), handlePacketScheduled() and handlePacketFiltered() one time for each packet and for each packet stream, and a module that keeps state changes it there. PacketFilterBase decides one time for each packet and keeps its verdict for a whole packet stream. In pull mode, a filter drops the packets that do not match in its own operations, not in canPullPacket(); ReceiveWithLifetime and EligibilityTimeFilter therefore no longer support pull mode. canPullPacket() of a scheduler offers the packet of the input that schedulePacket() selects, so a module that reads the offered packet before it pulls, such as TokenBasedServer, pulls that packet.

The results change where a module asked a query before it moved a packet. RedDropper and StatisticalRateLimiter decide with a random number that they drew in advance, and they draw one more number at initialization, so their simulations give other results with the same statistical behavior. TokenBucketClassifier, MultiTokenBucketClassifier and the color classifiers based on them take the tokens of a packet one time, and WrrClassifier moves its round only for a packet. OrdinalBasedDropper counts and StreamMerger records a streamed packet one time. LabelScheduler skips an empty input instead of crashing. DynamicClassifier creates a branch only for a packet; it refuses the reverseOrder parameter, which created more branches than classes; it always answers canPushSomePacket() with yes; and its new parameter aggregatorSubmoduleName names the submodule that gets the branches, which can be a pull scheduler.

A RedDropper with useEcn = true now marks ECN-capable IPv6 packets with Congestion Experienced, as it marked IPv4 packets; before, it dropped them. EcnMarker reads and writes the ECN field of the IPv6 Traffic Class too, and the EcnMarker module tags IPv6 packets. RedDropper reports an early drop with the reason CONGESTION and a drop at the capacity with QUEUE_OVERFLOW; before, the reason was OTHER_PACKET_DROP, so its packetDropCongestion statistic was always 0. CompoundPacketQueueBase now owns a packet that a child queue removes before it reports the drop.

This change requires the modification of C++ code that implements IPassivePacketSource or IPacketQueue directly, or extends the classifier, scheduler or filter base classes outside INET. See the migration guide.

The captured values of packet filters and the ownership fix of the compound queues were contributed by Miguel González-López.
