## What this series does well

Two things are worth naming, because both are rules that the last audited pull request broke.

**PR-SPLIT-UPSTREAM, done properly.** Commit 1 adds
`L3AddressResolver::getHostNameWithMacAddress()` — a shared networklayer capability — in its own
commit, *before* the 802.11 commit that needs it, and its message explains the generic need without
once naming 802.11: *"naming a peer by the address a model knows it by … takes both a lookup and a
naming convention, and neither belongs to the model that happens to need it first."* That is the
test the rule states, passed on the first reading. Compare [pr-1144.md](pr-1144.md) finding F-1,
where the same shape of change was buried inside a protocol commit.

**A test that states its claim and its counterfactual.**
`tests/module/AarfRateControlPerReceiver_1.test` says what it measures (54 Mbps to the near peer,
24.7 Mbps to the far one), and what the old behavior produced instead (29.6 Mbps blended, 380
packets to the far peer against 1350). A reader can judge whether the test establishes the claim
without running it, which is the whole point of `TR-CAT-MATCH`.

## Findings

### F-1 — Three fingerprints run the changed rate control, and nothing says what happens to them

**Rules:** [AR-QUAL-FINGERPRINT](../../../rule/architecture.md#ar-qual-fingerprint),
[TR-BASELINE-DELIBERATE](../../../rule/testing.md#tr-baseline-deliberate),
[PR-REQ-STORY](../../../rule/pull-request.md#pr-req-story). **Blocking for the merge, not for the
design.**

Commit 3 changes when the periodic rate increase starts. Before, the interval timer was
default-initialized, so the first interval elapsed at `t = interval`. After, it is seeded at first
use:

```cpp
state.timer = simTime(); // the interval starts when the station is first seen, not at t=0
```

The commit message states this deliberately and gives a good reason for it. **It is still a change
to the event trajectory of every scenario whose first transmission is not at t=0**, which is every
scenario. Both `AarfRateControl` and `OnoeRateControl` carry it.

Three checked-in fingerprint rows run `AarfRateControl`:

| Fingerprint row | Configuration |
|---|---|
| `showcases/wireless/ratecontrol/` | `-c AarfRateControl -r 0` |
| `showcases/visualizer/canvas/instrumentfigures/` | `-c General -r 0` |
| `examples/wireless/ratecontrol/` | `-c Mac -r 0` |

The branch touches no file under `tests/fingerprint/`. Two outcomes are possible and the series does
not say which: either the fingerprints do not move, and that fact belongs in the pull request
description; or they do, and a baseline commit is owed under
[PR-SPLIT-BASELINE](../../../rule/pull-request.md#pr-split-baseline) with the reason under
[TR-BASELINE-PROVENANCE](../../../rule/testing.md#tr-baseline-provenance).

**What would close it:** run those three configurations and state the result. Note that the
per-receiver refactor alone is probably trajectory-neutral here — all three scenarios have a single
peer — so the timer seeding is the one thing to watch.

### F-2 — The contract change is announced to users but not to the framework's own documents

**Rules:** [AR-ORG-CONTRACTS](../../../rule/architecture.md#ar-org-contracts),
[RR-BREAK-MIGRATE](../../../rule/release.md#rr-break-migrate). **Minor.**

`IRateControl::getRate()` becomes `getRate(const MacAddress&)`. This is handled better than most:
the WHATSNEW entry names the break, names who it affects (a rate control implemented outside INET),
and names who it does not (a model that only configures one).

What is missing is the migration guide. `RR-BREAK-MIGRATE` asks that a breaking change ship with the
instructions to repair it, and `doc/src/migration-guide/` is the user-facing home for those. A
WHATSNEW note is the announcement; the migration guide is where a user who upgrades two releases
later will look.

**What would close it:** a short entry in the migration guide, or a stated decision that WHATSNEW is
enough for a break this small.

### F-3 — Two new statistics, and no runnable example that shows them

**Rules:** [AR-OBS-SIGNALS](../../../rule/architecture.md#ar-obs-signals),
[R-DOC-RUNNABLE](../../../requirement/accepted-requirements.md#r-doc-runnable). **Minor, and
arguably out of scope.**

The series adds `dataratePerStation` on `AarfRateControl` and `OnoeRateControl`, and a
`dataFrameBitratePerReceiver` parameter on both rate selections. The module tests exercise them, but
`showcases/wireless/ratecontrol/` — the page a user reads to understand rate control — is untouched,
so the new per-station view is not visible anywhere a user would look.

**What would close it:** a paragraph and a chart in that showcase, or a stated decision to leave it
for a follow-up.
