## Findings

### F-1 — Behavior changes, three fingerprints cover it, and no baseline commit exists (PR-SPLIT-BASELINE)

`359e5b690e` changes the simulation trajectory in two ways:

- the adaptive state is kept per receiver, so a transmitter serving several peers no longer blends
  their feedback into one rate;
- `state.timer = simTime()` seeds the interval timer when a station is first used, in place of a
  timer that ran from zero. This moves the first periodic rate increase **even with a single peer**,
  whenever the first data frame is sent later than one `interval`.

Three checked-in fingerprints run this code:

| Row | Config |
|---|---|
| `tests/fingerprint/examples.csv:663` `/examples/wireless/ratecontrol/` | `-c Mac`, `AarfRateControl` |
| `tests/fingerprint/showcases.csv:320` `/showcases/wireless/ratecontrol/` | `-c AarfRateControl` |
| `tests/fingerprint/showcases.csv:133` `/showcases/visualizer/canvas/instrumentfigures/` | `AarfRateControl` |

The series contains no baseline commit, and the pull request says nothing about fingerprints. One of
two things must happen before merge: either a run shows the three rows unchanged, and the pull
request says so — or the branch gets a baseline commit of its own, after the behavior commit, with
the causal explanation (AR-QUAL-FINGERPRINT, AR-QUAL-TRACEABILITY). The second showcase already
carries the comment `seed-set = 1    # only for unchanged fingerprints`, which shows how sensitive
this scenario is.

### F-2 — The branch is 191 commits behind master (PR-SERIES-LINEAR)

The merge base is `5db7070295` of 2026-06-22. The rate selection, rate control and statistics code
all moved in master since then. Rebase, then produce the evidence of F-1 and F-3 on the rebased

### F-3 — No reproducible evidence, and an undeclared contract change (PR-REQ-STORY, PR-REQ-ARCH)

The description ends with "*Testing confirmed via `examples/wireless/hiddennode` with per-station
vectors keyed by peer node name*". That is an observation, not evidence: no command, no
configuration, no status, no fingerprint result. The rules ask for the exact commands and their
results, and for the architectural surface the change touches.

Two contracts change and neither the description nor `WHATSNEW` mentions it:

- `IRateControl::getRate()` gains the receiver address. This is a pure virtual method of a NED
  `moduleinterface` contract (AR-ORG-CONTRACTS), so every rate control implemented outside INET
  stops compiling. A compile break is the safe kind, but it belongs in `WHATSNEW` (AR-DIST-COMPAT).
- `IRateSelection` gains a static `emitDatarateSelected()` helper — a contract that now carries an
  implementation, and an include of `networklayer/common/L3AddressResolver.h`.

### F-4 — The test of commit 2 arrives in commit 4 (PR-SPLIT-ONE-CHANGE, AR-QUAL-TESTS)

`tests/module/AarfRateControlPerReceiver_1.test` proves the per-receiver adaptation of commit 2, but
it ships with commit 4, which adds the per-station statistic the test observes. The message states
the dependency openly, which is the right thing to do, and the test genuinely needs the observable.

The cleaner order removes the tension: record the per-station data rate first — the statistic is
meaningful with the old rate control too, it just shows one value per station — then change the
adaptation and let it bring its test. As it stands, commit 2 changes 802.11 behavior with no test of
its own, and a bisect that stops on commit 2 or 3 has nothing to run.

### F-5 — Whitespace rides along (PR-SPLIT-WHITESPACE)

## Architectural notes — beyond the commit rules

1. **Observation work inside the MAC (AR-ORG-VIS-SPLIT, AR-OBS-SIGNALS).** Both signal emitters now
   resolve a *host name* — `L3AddressResolver().getHostNameWithMacAddress(...)` sweeps the interface
   tables of the network — and emit it as the signal details. The rule says a protocol module
   computes protocol behavior and emits signals, while naming and recording happen outside it. The
   model owns the receiver MAC address; the name is a presentation of it, and the recorder or the
   visualizer could resolve it. Two facts soften this: three link-layer files in master already
   include `L3AddressResolver`, and the per-frame emitter is guarded by
   `emitter->mayHaveListeners(datarateSelectedSignal)`, which I verified in
   `IRateSelection::emitDatarateSelected()`. This is a T5 judgment call for the maintainer, not a
   mechanical violation.
2. **No new dependency violation.** `check-architecture.sh` run at the head of this branch reports
   only the two known `AR-ORG-VIS-SPLIT` entries (`MobilityBase.cc`, `OsgEarthGround.cc`), which are
   ledger row AV-VIS-01. The branch adds none.
3. **The parameter is unit-correct (AR-CFG-PARAMS).** `dataFrameBitratePerReceiver` is an `object`
   parameter, so it cannot carry `@unit`, but the code reads each value with
   `value.doubleValueInUnit("bps")`, so `54Mbps` in an ini file is converted, not assumed. Errors
   name the offending entry. The deferred resolution to the first transmitted frame, instead of
   `initialize()`, is the correct answer to the undefined module order inside
   `INITSTAGE_LINK_LAYER`.
4. **Duplication.** The ~30 lines of per-receiver resolution are added twice, to `RateSelection.cc`
   and `QosRateSelection.cc`, and the NED parameter to both `.ned` files, because the two classes
   share no base. This mirrors the duplication that already exists between them, but a shared helper
   would be better.
5. **Test coverage (AR-QUAL-TESTS).** One test file for six commits. `dataFrameBitratePerReceiver`
   and the `datarateSelected` tagging have no test, and both are easy to test at module level.
