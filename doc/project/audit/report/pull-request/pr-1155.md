### F-2 — No release note, for a change that breaks users four ways

**Rules:** [RR-WHATSNEW](../../../rule/release.md#rr-whatsnew),
[RR-BREAK-MIGRATE](../../../rule/release.md#rr-break-migrate),
[RR-DEPRECATE-FIRST](../../../rule/release.md#rr-deprecate-first). **Blocking. Unchanged.**

### F-5 — `ITcpRecovery` holds five no-op default bodies

**Rule:** [AR-ORG-CONTRACT-PURITY](../../../rule/architecture.md#ar-org-contract-purity).
**Finding. New — the rule was written on 2026-09-07, six days after the first audit.**

The head carries **17** interface violations against master's 15. One of the two is
`IIeee80211Band`, which this branch does not touch — master repaired it after this branch's base, so
that difference is staleness, not fault. The other is this branch's own:

```cpp
class INET_API ITcpRecovery {
    virtual bool isDuplicateAck(const TcpHeader *, uint32_t) = 0;
    virtual void receivedAckForUnackedData(uint32_t) = 0;
    virtual void receivedDuplicateAck() = 0;
    virtual void segmentsAcked(uint32_t, uint32_t) {}      // ← five no-op defaults
    virtual void dataSent(uint32_t) {}
    virtual void segmentRetransmitted(uint32_t, uint32_t) {}
    virtual void onRexmitTimeout() {}
    virtual void reoTimeout() {}
};
```

Three classes implement it: `Rfc5681Recovery`, `Rfc6582Recovery`, `Rfc6675Recovery`. A recovery
algorithm that does not care about one of the five gets silence — which is convenient today and is
the exact shape that made `IIndicatorFigure::getNumSeries()` a silent break in
[#1125](pr-1125.md) F-2. Rename one of the five and every out-of-tree recovery keeps compiling with
its override no longer called.

This is a **new interface in a new architecture**, which is the cheapest possible moment to get it
right: there is no out-of-tree implementor yet to break.

**What would close it:** make the five pure and add `{}` to the three implementors where the
behavior really is nothing — three one-line overrides each, and each states its own answer. A
`TcpRecoveryBase` is the alternative if the defaults grow beyond nothing.

### F-7 — Seventeen commits have no body at all

**Rules:** [PR-MSG-BODY](../../../rule/pull-request.md#pr-msg-body),
[PR-MSG-WHY](../../../rule/pull-request.md#pr-msg-why). **Finding. New, and it is a fault in the two
earlier passes of this report as much as in the branch.**

**Both earlier versions of this report marked `PR-MSG-WHY` as a PASS**, with the words *"symptom,
cause and decision throughout"*. That was written after reading the messages that have a body. **17
of the 61 commits have none** — no body, no trailer, nothing under the subject line. The rule as it
then read said *"the body gives the reason"*, which is vacuously satisfied by a commit that has no
body, so nothing in the rule set asked the question and neither pass thought to.

Twelve are above the line the new gate draws at 50 changed lines:

| Lines | Commit | Subject |
|---:|---|---|
| 860 | `81713e23d9` | tcp: size segments against the space options actually leave |
| 769 | `6d3b0fdcdb` | tcp: judge loss by transmission time (RFC 8985) |
| 683 | `710b18208c` | tcp: TCP Fast Open (RFC 7413) |
| 579 | `2fec57756c` | tcp: connection plumbing the modern features share |
| 528 | `7327e5c5d2` | tcp: Accurate ECN |
| 476 | `eb549a12a5` | tcp: undo a reduction that turned out to be unnecessary |
| 238 | `4b46417a58` | tcp: probe the tail rather than waiting out the timeout |
| 189 | `1a9200e2a3` | tcp: separate the receive buffer from the advertised window |
| 110 | `3616a5a5ca` | tcp: keepalive probing (RFC 1122 4.2.3.6) |
| 76 | `a4317c0d3e` | tcp: the socket options the new behavior exposes |
| 58 | `838e6d254f` | tcp: learn how far the path reorders |
| 53 | `8bbf0d575b` | tcp: retransmission, persist and handshake timing |

Five more are below it and are the reviewer's to judge, not the gate's.

**The subjects are good, and that is the trap.** *"undo a reduction that turned out to be
unnecessary"* and *"probe the tail rather than waiting out the timeout"* read like a reason, so a
reader skimming `git log` feels informed. They are not reasons; they are restatements of what the
code now does. Under which condition was the reduction unnecessary, and what happens if the undo
fires wrongly? Which timeout, and why is a probe better than waiting? A 683-line implementation of
RFC 7413 names the RFC and says nothing about what of it was implemented, what was left out, or
which of its options INET now negotiates.

**This is out of character for the branch and for the project.** The other 44 commits include the
best baseline provenance this audit has seen (F-3). Across master's last 300 commits, only 4 % of
commits over 50 lines have no body, and six of the nine that do are the kinds where the change
explains itself. Across the other six audited pull requests the new gate reports **zero**. This
branch reports twelve.

**What would close it:** a body on each of the twelve. The author plainly has the reasons — the
neighbouring commits in the same series demonstrate it — so this is writing down what is already
known, not discovering it.

### F-8 — The summary silently reports the wrong numbers when two parsers are missing

**Rules:** [AR-QUAL-TRACEABILITY](../../../rule/architecture.md#ar-qual-traceability),
[DR-HEADER](../../../rule/documentation.md#dr-header) — the `generated, do not edit` status is a
promise that the file can be rebuilt. **Blocking for the audit process, not for the branch.**

This pass began by regenerating the summary. It produced:

```
**210** added; **37** removed; **10** changed; ... **1** split across classes.
```

against the **547 / 49 / 22 / … / 4** the file already held, on a branch whose head, merge base and
diffstat had not moved and with the tool at the same commit, `dbb5f21`. The cause is that
`opp_nedtool` and `opp_msgtool` were not on the `PATH`. **The run wrote nothing to stderr and
exited 0.** With the parsers on the PATH the numbers return to 547 and the body is byte-identical
to the recorded file.

So a missing parser removes **337 of the 547 additions** — every NED and every message fact — and
the report says so nowhere. Worse, the preamble of the generated file states that "NED and message
facts come from `opp_nedtool` and `opp_msgtool`" while none were extracted, so the document asserts
a provenance it does not have.

**This nearly corrupted this report.** A reader who trusted the regenerated file would have
concluded that the branch adds 210 things instead of 547, and that the earlier audit overstated the
change by a factor of two and a half.

**What would close it:** `opp_summarize_changes` fails, loudly, when a parser it names is not
runnable. A second, cheaper guard: the generated preamble names the parser versions it actually
ran, so a reader can see their absence. Until then,
[review-a-pull-request.md](../../../guide/review-a-pull-request.md) must carry the `PATH` export
beside the command, and this report's *How the audit was made* now does.

**The tool is `opp_repl`, not INET**, so the repair is not in this repository.
