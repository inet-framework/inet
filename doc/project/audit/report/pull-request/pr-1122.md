## What this series does well

**A commit message that tells the reviewer how to read it.** Commit 1: *"Whitespace-only except for
the inverted condition and the hoisted return — review with a whitespace-ignoring diff."* Commit 2:
*"the lines byte-identical (review with `--color-moved`)."* Both are exactly the cheap verification
that [PR-SPLIT-WHITESPACE](../../../rule/pull-request.md#pr-split-whitespace) and
[PR-SPLIT-MECHANICAL](../../../rule/pull-request.md#pr-split-mechanical) exist to make possible, and
the author states which command produces it.

**Defect messages that name the failure, not the fix.** Commit 4 does not say "fix initialization
order"; it says what breaks and how: *"`ModuleRefByGate::reference()` resolves the peer eagerly by
walking the connection — with `mandatory=false` it silently stores a nullptr that nothing ever
re-resolves, leaving a permanently null consumer whose `canPushPacket()` throws and whose
`pushPacket()` quietly degrades to `send()`, bypassing back-pressure."* A reader two years from now
can search for that symptom.

**A contract stated before it is relied on.** Commit 6 writes down that classification is a *query*
and must be free of side effects — *"the capacity checks classify the very packet whose delivery
classifies it again"* — and gives `-1` a documented meaning that three classifiers already used
informally. The behavior change then follows the contract instead of the contract following the code.

**The test ratio.** Four new files under `tests/queueing/`, 377 of the 609 added lines. For a series
that is mostly a refactor and four defect repairs, that is the right shape.

## Findings

### F-1 — One subject is 75 characters

**Rule:** [PR-MSG-SUBJECT](../../../rule/pull-request.md#pr-msg-subject). **Trivial.**

`5892ece97f` — *"diffserv: answer canPushPacket for a packet that goes to the default output"* — is
three characters over the 72 the rule asks for. *"diffserv: answer canPushPacket for a default-output
packet"* is 58 and says the same.

### F-2 — One stray blank line rides in the unindent commit

**Rules:** [PR-SPLIT-DRIVEBY](../../../rule/pull-request.md#pr-split-driveby),
[PR-SPLIT-WHITESPACE](../../../rule/pull-request.md#pr-split-whitespace). **Trivial.**

Commit 1 removes a trailing blank line at the end of `DynamicClassifier.h`. It is unrelated to the
unindent in the `.cc`, it is the commit's only change to that file, and it is what
`check-commits.sh` reports.

The logic part is a different matter and is **not** a finding: inverting the condition into an early
return is inseparable from the unindent — you cannot have one without the other — and the message
discloses it and names the command that verifies it. See F-3.

### F-3 — One sentence of WHATSNEW overstates its own case

**Rule:** [RR-BREAK-MIGRATE](../../../rule/release.md#rr-break-migrate). **Minor.**

The entry closes: *"Existing simulation models are unaffected: the defaults reproduce the previous
behavior."* Two paragraphs above, it says the `reverseOrder` parameter *"is refused by
DynamicClassifier"*. A model that set `reverseOrder = true` on a `DynamicClassifier` is affected, and
affected hard: it now fails in `initialize()`.

Refusing loudly is the right call — the parameter had nothing left to act on, and a silently ignored
parameter is worse than an error ([QR-ERR-THROW](../../../rule/quality.md#qr-err-throw)). The finding
is only that the closing sentence contradicts the paragraph above it, and a user who reads the
summary and stops will be surprised.

**What would close it:** *"Existing simulation models are unaffected unless they set `reverseOrder`
on a `DynamicClassifier`."* No in-tree configuration does, and no fingerprint covers the one
tutorial that uses the module.

## Two notes that are not findings

**No baseline is owed.** `DynamicClassifier` has exactly one in-tree user,
`tutorials/protocol/Network90.ned`, and no fingerprint row covers it. Nothing else in the tree
instantiates the module, so the behavior changes here reach no recorded expectation.

**A gap in our own rule, again.**
[PR-SPLIT-WHITESPACE](../../../rule/pull-request.md#pr-split-whitespace) says a whitespace commit
*"must not contain one line of functional change"*. Commit 1 cannot obey that and still exist: an
unindent of a conditional body **is** the inversion of the condition. The author did the right
thing — disclosed the exception in the message and named the command that verifies it — and the rule
as written still forbids it. That is the second such gap this author's work has exposed; the first is
[pr-1125.md](pr-1125.md) F-3. Both are worth a clause when `pull-request.md` is next touched.

## A limitation this audit exposed in the change summary

The summary first reported this pull request as **2 additions**, and missed its most significant
change: `PacketClassifierBase::createGateForPacket()` and `canCreateGateForPacket()`, the new
extension hooks that the whole series exists to add. Both are `protected`, and the summary reported
only the public surface.

**A protected virtual on a base class is an interface** — the one its subclasses implement, and the
one a new model writes against. The extractor now reports them as a separate *extension points* kind,
and the summary shows 11 additions, of which 9 are hooks. Fixed in `opp_repl` during this audit.
