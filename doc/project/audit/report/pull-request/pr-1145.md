## What the change is

Four movements across thirteen commits:

1. **The AP and STA HT state work of [#1175](pr-1175.md)** — commits 1 and 2.
2. **Corrections to the PHY tables**, commit 3: HT MCS 32, 73 and 76 definitions per IEEE
   802.11-2024; HT and VHT signal-mode symbol timing using the long symbol duration independently of
   the data guard interval (Table 19-6, Table 21-5); short-guard-interval airtimes rounded to the
   4 µs boundary for mixed format (Eq. 19-90, Eq. 21-109) and left raw for greenfield (Eq. 19-92).
3. **Guard interval as a first-class parameter** — a completed mode-set catalog, guard-interval
   qualified lookups, a `dataFrameGuardInterval` NED parameter on both rate selections.
4. **A transactional mode-set change**, commits 10 to 13: a typed `IIeee80211ModeSetListener`
   contract with a `saveModeSetState()` rollback closure, so a failed listener cannot leave the
   radio and an arbitrary prefix of its consumers on a new catalog.

**2352 of the 3260 added lines are tests** — seven test files. For a change whose difficulty is
ordering and failure, that is the right investment, and the last four commits each say the
regression fails before the fix.

### The new contract is pure

`IIeee80211ModeSetListener` holds a defaulted virtual destructor and three pure virtuals, in a new
`contract/packetlevel/` package. That is
[AR-ORG-CONTRACTS](../../../rule/architecture.md#ar-org-contracts) and
[AR-ORG-CONTRACT-PURITY](../../../rule/architecture.md#ar-org-contract-purity) both satisfied, and
`saveModeSetState()` returning a `std::function<void()>` is a rollback token rather than state on
the interface — the right shape for a transaction.

## Findings

### F-1 — Behavior moves and the series says nothing about the fingerprints

**Rules:** [AR-QUAL-FINGERPRINT](../../../rule/architecture.md#ar-qual-fingerprint),
[PR-SPLIT-BASELINE](../../../rule/pull-request.md#pr-split-baseline),
[PR-REQ-STORY](../../../rule/pull-request.md#pr-req-story). **The finding that blocks the merge.**

Commit 3 changes what an 802.11n or 802.11ac transmission costs in time:

> Fix HT and VHT signal mode symbol timing to use long symbol duration independently of data GI.
> Round mixed-format HT and VHT short-GI data airtimes up to 4 µs / long-GI symbol boundaries.

and it corrects three MCS table entries. Both change the event trajectory of any simulation that
uses those modes. **The branch touches no file under `tests/fingerprint/`, and no message mentions a
fingerprint.**

Two rows are directly exposed:

| Fingerprint row | Why |
|---|---|
| `examples/wireless/lan80211ac/` | runs an `ac` operating mode |
| `showcases/wireless/txop/` | runs an `n` operating mode |

The exposure is small, which is the good news, and it is not zero, which is the finding. Either
those two rows do not move — and that belongs in the pull request description — or they do, and a
baseline update is owed in the commit that moves them, with the reason
([TR-BASELINE-PROVENANCE](../../../rule/testing.md#tr-baseline-provenance)).

This is the same shape as [#1124](pr-1124.md) F-1 and it is worth saying why it keeps recurring:
**a small exposure is the case where a run is skipped.** Two rows is exactly the number that feels
safe to assume about.

**What would close it:** run those two configurations and state the result.

### F-2 — A default body enters an interface, and it returns a sentinel

**Rule:** [AR-ORG-CONTRACT-PURITY](../../../rule/architecture.md#ar-org-contract-purity).
**Finding, and it is new: master is at 15 violations, this head at 16.**

Commit 3 adds to `IIeee80211DataMode`:

```cpp
virtual const simtime_t getGuardInterval() const { return -1; }
```

`IIeee80211DataMode` is a flat interface — there is no `Ieee80211DataModeBase` — and **seven** data
mode classes inherit it directly. Three override the new method: `Ieee80211OfdmDataMode`,
`Ieee80211HtDataMode`, `Ieee80211VhtDataMode`. The other four — FHSS, DSSS, HR-DSSS, IR — take the
`-1`.

For those four the answer *is* "no guard interval", so the intent is sound. The rule's objection is
not to the value but to where it lives: a default body in an interface means a new data mode written
tomorrow inherits an answer silently, and a rename of the method leaves every out-of-tree data mode
compiling with its override no longer called. That is the failure the rule exists for, and
[#1125](pr-1125.md) F-2 is the same method shape in the same subsystem.

**What would close it, cheapest first:** make it pure, and add `{ return -1; }` to the four non-OFDM
data modes — four one-line overrides, each stating its own answer. A `Ieee80211DataModeBase` is the
alternative and it is more than this needs.

### F-3 — No release note

**Rules:** [RR-WHATSNEW](../../../rule/release.md#rr-whatsnew),
[RR-BREAK-MIGRATE](../../../rule/release.md#rr-break-migrate). **Finding.**

`WHATSNEW` is untouched. What a user or an out-of-tree model meets:

| What changes | Who it reaches |
|---|---|
| HT MCS 32, 73, 76 definitions and HT/VHT symbol timing are corrected | **every 802.11n and 802.11ac result changes** — the most consequential item, and the one a user must know about |
| `Ieee80211Mac`, `Ieee80211MgmtBase`, `RateSelection` and `ModeSetListener` gain `IIeee80211ModeSetListener` as a base | an out-of-tree subclass of any of the four |
| `dataFrameGuardInterval` on both rate selections | additive; worth an entry as a new capability |

The corrected results are the reason this one matters more than the previous four. A user whose
802.11n numbers move after an upgrade has no way to learn why.

**Not a break, and worth stating so it is not mistaken for one:** `getMode` and `findMode` gain a
`simtime_t guardInterval = -1` parameter. Every existing three-argument call still compiles. The
summary lists the four as *removed* and four more as *added*, which overstates it — see the third
note.

### F-4 — Two versions of one commit are open at the same time

**Rule:** [PR-REQ-TOPIC](../../../rule/pull-request.md#pr-req-topic). **Finding.**

`8ac5675c9c` here and `843995a4d0` in [#1175](pr-1175.md) carry the same subject and differ by
exactly three lines. This branch **does not** have:

```cpp
int getConfiguredSecondaryChannelOffset() const { return configuredSecondaryChannelOffset; }
```

nor the two test assertions that read it. That member is precisely the one
[#1175](pr-1175.md)'s note questioned as called only from tests.

**This branch's version is the newer one** — committed 2026-09-10 10:54, against #1175's
2026-09-09 20:34 — and it is the version *without* the getter. So the disagreement is probably
already settled in the author's mind, and settled the way
[AR-EXT-MINIMAL-SURFACE](../../../rule/architecture.md#ar-ext-minimal-surface) would settle it: a
member whose only readers were two test assertions is gone.

What remains is that both versions are open at once. Whichever merges first, the other must rebase,
and the rebase will not be clean on that file.

**What would close it:** decide which version is intended, and make the other branch match — or
close #1175, whose two commits are both here.
