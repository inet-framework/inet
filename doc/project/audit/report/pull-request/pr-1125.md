## Findings

### F-1 — The stack is 191 commits behind master (PR-SERIES-LINEAR) — **open**

The merge base is `5db7070295` of 2026-06-22, unchanged since the first audit. The description now
says so plainly, which is honest, but the state remains: the visualizer, the figure classes and the
statistic recording path all moved in master during those 191 commits. Every result reported for
this branch describes a two-month-old tree. Rebase, then re-run the two module tests and the new
fingerprint row.

### F-2 — Fingerprint status of the stack — **answered, but recorded in the wrong pull request**

The description states that the three checked-in rows that exercise `AarfRateControl` match the
recordings at both the merge base and the head of the base pull request, and that the `tyf`
ingredient was already stale at the merge base and does not change across the branch. That answers
the question this audit raised, and it is falsifiable, which is what PR-REQ-STORY asks for.

Two small things remain. The statement carries no command, so nobody can repeat the run from the
text alone. More importantly, the behavior it clears belongs to **PR #1124**, not to this one: a
reviewer of #1124 reads only #1124. Repeat the fingerprint statement there (see
[pr-1124.md](pr-1124.md) F-1).

### F-3 — **Fixed.** One capability per commit

`bb3ba4945f` adds `splitBy` together with the item model that both parameters need; `b28198053e`
adds `groupBy` on top, with the two module tests. Both messages explain why the decisions are
independent, and the second one states the accepted combinations and the reason for each
restriction.

### F-4 — **Fixed.** The rename is its own commit, with a compatibility note

`d01e98ca0c` renames `IIndicatorFigure::getNumSeries()` to `getNumItems()` and the first parameter
of `setValue()` to `index`, touching only `PlotFigure` and `FigureRecorder`, and ends with "*Pure
rename, no behavior change*". The `WHATSNEW` entry it carries names the exact silent-failure mode
the audit was worried about: because `getNumSeries()` had a default body returning 1, an out-of-tree
indicator figure keeps compiling, its override stops being called, and the figure silently reports
one item. The entry tells such authors to rename their override. This is the model form of a
mechanical commit (PR-SPLIT-MECHANICAL, AR-DIST-COMPAT).

### F-5 — **Fixed.** Evidence, a fingerprint row, and tests

- The description states the build passes at all seven commits (PR-SERIES-BUILDS).
- `6035d6e298` adds `/examples/visualizer/statisticbars/, -f omnetpp.ini -c Packets -r 0` to
  `tests/fingerprint/examples.csv` with real recorded values, so CI now runs the new example.
- `b28198053e` adds `tests/module/StatisticVisualizerItems_1.test` and `_2.test`. Both run under
  Cmdenv's fake GUI, which is what makes `refreshDisplay()` execute — without it the visualizer is
  inert and such a test passes for the wrong reason. The first exercises the whole path down to
  `BarChartFigure` sizing, labelling, scaling and layout; the second proves that grouping several
  items onto a gauge is rejected instead of silently displaying one of them, and it also proves the
  fake GUI really runs.

**Residual, small:** `splitBy` has no automated coverage. The two tests cover `groupBy =
"networkNode"`; the `Flow` and `Throughput` configurations of the example exercise splitting, but the
single fingerprint row runs `-c Packets` under Cmdenv without a GUI, where the visualizer does
nothing. A third module test in the shape of the two existing ones would close it.

### F-6 — **Fixed.** No whitespace noise

`git diff -w --ignore-blank-lines` against every commit of the series finds nothing, and no file
gains or loses a trailing blank line end to end.

## Rule gaps found by this audit

1. **Stacked pull requests are not covered.** [pull-requests.md](../../../rule/pull-request.md) says nothing
   about a pull request whose base is another topic branch under review. Write down the practice
   used here: the description names the base pull request, the reviewable scope is the commits above
   that base, and the base merges first. Without the rule, a reviewer who reads `git log` against
   master audits the wrong scope.
2. **PR-SPLIT-BASELINE needs one word of scope.** The rule targets *regenerated* expectations. A
   **new** fingerprint row for **new** content is not a baseline update — it is the test of the thing
   it ships with, and it belongs in the same commit, exactly as `6035d6e298` does it. State that, so
   the rule is not read as "every `.csv` change must be a separate commit".
