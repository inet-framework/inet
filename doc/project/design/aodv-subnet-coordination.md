# AODV subnet authority and cooperation

> **Kind:** design · **Status:** draft · **Seal:** none · **Owns:** — · **Stands on:** [RFC 3561 sections 7–9](https://www.rfc-editor.org/rfc/rfc3561.html#section-7), [implementation plan](../../../plan/pending/aodv-remaining-features.md)

This design defines an opt-in INET profile for authoritative subnet replies, recovery of a retained subnet sequence floor, and election among trusted routers on one common attached network. It supplies the C9a contract required before C8–C10 implementation. It does not claim an allocated AODV extension or interoperability with an independently defined IPv6 AODV protocol.

## Why requests need a prefix domain

The current RREQ sequence field describes a requested host. A retained aggregate instead causes U=1,D=1 and numeric zero. Thus, after upstream failures advance an aggregate from sequence 5 to 12, an authority still holding 5 receives no indication that 12 is needed. Incrementing once per reply cannot guarantee that a bounded discovery recovers.

The profile uses a configured `subnetExtensionType` in 128–255; zero disables it and preserves the legacy host-floor behavior. All AODV participants in a subnet-profile scenario must select the same value. Documentation examples use 253 solely as a scenario-local identifier, not an IANA assignment. Unsupported mandatory extensions are rejected without route or observation changes. Export configuration requires the profile to be enabled; enabling it alone does not advertise any subnet.

The extension has Type, Length=5, Prefix Length, and a big-endian uint32 Sequence Floor. The normalized prefix derives from the requested destination and prefix length. Exactly one such extension is allowed. The prefix must be an aggregate representable by the selected address family. RREQs carrying it retain U=1,D=1 and a zero base destination sequence field. Ordinary known-host floors remain in the ordinary RREQ fields and must not be combined with this marker.

At actual request creation, the originator includes the retained exact aggregate's floor. For an extension-free U=1 request, a supporting relay may attach its applicable known aggregate floor and set D before forwarding; an unknown originator must not lose recovery merely because retained history lives on an intermediate hop. Never attach a marker to a U=0 host-floor request. Once a request has a marker, a relay may promote the floor only from its own known record for that exact normalized prefix, without replacing it with a different prefix domain. `/24`, `/25` and host records never exchange counters. A relay preserves the extension when it lacks matching knowledge. Cached aggregate replies remain disabled by D. An exact-host destination may still answer for itself through the existing host contract.

An authority without valid counter knowledge copies the first known same-prefix floor before doing serial comparisons. With two known counters, it adopts a strictly newer floor, preserves an equal/older floor, and suppresses a reply for the exactly half-range ambiguity. Its RREP retains the requested member address and carries the configured prefix and current subnet counter. A matching inactive upstream aggregate can accept the resulting equal-or-newer reply. An authority for a broader prefix cannot satisfy a retained more-specific floor; it forwards rather than generating a futile broader answer. A more-specific authority may answer using its independent counter because it supplies a separate, more-specific route. Known independent host floors still require host-specific information.

## Authority state and lifetime

AODV owns one record per configured prefix: canonical prefix, attached/output interface identity, subnet sequence and validity, interface-qualified precursor set, and current availability. This is local export state, not a second active forwarding table. Native routes remain responsible for data forwarding. Single-authority configuration adds no candidate messaging.

Initialize a new authority's counter to zero with no known history. Its first eligible reply to an unknown-floor request establishes zero as valid, unless a known same-prefix floor has already been adopted. Do not increment it merely for repeating an unchanged advertisement. Advance a known counter once when an advertised prefix becomes unavailable, and adopt same-domain floors from validated requests or candidate announcements. Unknown state stays unknown until a known floor or an eligible first advertisement establishes it. Use existing 32-bit serial arithmetic throughout. Independent node sequence state remains independent.

Same-instance stop/start may preserve configured-prefix counters, but simulated crash clears their validity to model sequence loss. In either case, remove pending advertisements, precursor obligations and transient candidate observations. A restarted authority observes the existing DELETE_PERIOD recovery hold before replying. Requests and candidate announcements may restore exact-prefix knowledge during the hold. After it, a request with a known subnet floor is adopted before the reply. A genuinely unknown-floor request may establish a fresh zero-counter domain only when no retained floor has been learned; do not present the recovery hold itself as reconstruction of missing subnet knowledge.

Prefix withdrawal uses the authority record's saved precursors. An authoritative RREP creates a precursor at actual send, using the outgoing upstream next hop/interface. If the export becomes unavailable, send the normalized prefix and once-advanced counter through the existing RERR budget and partition code. A missing individual member yields ICMP without invalidating the aggregate. A burst of table notifications is reconciled once after the synchronous native-table operation; replacement routes or IPv6 in-place deleted/added notifications must not cause a false withdrawal.

## Candidate announcements

Multi-router operation is a bounded cooperation profile, not a consensus service. Each exported-prefix XML entry uses `candidates="192.0.2.1 192.0.2.2"` for its finite common candidate list and `coordinationInterface="eth0"` for its coordination interface; absence of candidates selects single authority. Candidate identities are the routers' addresses on that common network. They are distinct from the last hop of a relayed RREP and may differ from AODV's primary originator address. Every participant must configure the same candidate list, prefix and timing assumptions. Proposed parameters are `subnetAnnouncementInterval` for H (default 1s), `subnetAnnouncementDelay` for the delivery bound D (default 10ms), and `subnetCoordinationPort` (default 655).

Assumptions are trusted participants, fail-stop crashes, a connected coordination network, and announcement delivery within configured bound D. Announcements occur immediately on candidacy change and then every H. H and D are positive representable durations. The profile does not guarantee global exclusion during partitions or unbounded loss. An observed down/unusable coordination interface disables that candidate. Tests of a violated delivery assumption must report the unsupported interval and assert eventual convergence after connectivity returns, not silently claim partition safety.

Use a separate configurable UDP endpoint, default port 655, bound to a dedicated socket. Validate that it differs from the configured AODV `udpPort` whenever coordination is enabled. Do not add an unknown packet type to legacy AODV's UDP 654 dispatcher. Announcements carry address family, eligibility flag, prefix length, subnet sequence validity/value, candidate address and canonical prefix. Provide a serializer with exact size/range checks. Accept an announcement only on the configured coordination interface, from a listed candidate whose declared address matches the IP source and whose prefix matches exactly. Candidate packets never create data discovery, forwarding routes or link-observation deadlines. Reserve/classify the coordination endpoint before the AODV netfilter hook's early data observation, including malformed traffic on that endpoint; callback dispatch alone is too late when the coordination interface is also a selected ad hoc link.

A candidate announces its physical export eligibility before its joining wait finishes, so an incumbent hears a lower candidate and stops before that candidate can answer. Every false-to-true eligibility transition starts a fresh qualification wait, including restoration of an external route or attached prefix, not just module startup. It may answer only after H+D plus one simulation tick, its applicable reboot hold, and selection as the lowest eligible address. The extra tick resolves the inclusive delivery-bound tie without changing event priorities. Each observation remains live through `lastReception + H + D`; remove it only after that deadline. With reliable bounded delivery, a live lower candidate cannot time out. After a fail-stop crash, timeout can elect the next candidate because the old candidate cannot continue advertising or answering under the stated failure model.

An announcement transfers known exact-prefix sequence state. It cannot replace request-floor propagation: an upstream router may have advanced its own retained counter beyond the last announcement. On a returning lower candidate, existing candidates suppress answers when they receive its eligible announcement; the newcomer waits before answering and adopts available same-prefix history. A withdrawn candidate announces eligibility false, and is excluded immediately by receivers. At a healed partition, fresh candidate information restores lowest-address selection; request floors restore the relevant retained freshness before replies. No claim is made about safety during the unsupported partition interval.

The second socket is dispatched by socket identity. Start creates/reopens it only when configured candidates require it and joins the native IPv6 control multicast group on its coordination interfaces. Before graceful close, snapshot the IDs of actually opened sockets as pending close obligations, and remove each only on its matching close callback. Do not infer acknowledgment from `isOpen()`: `UdpSocket::close()` changes its local state before the callback arrives. A never-opened coordinator creates no obligation. Crash destroys both. Old close indications cannot complete a newer socket generation. Announcement and candidate-expiry events are canceled on lifecycle cleanup. A same-family interface readdressing updates bindings/membership and restarts candidate qualification, without calling lifecycle handlers on an operating module.

## Verification and compatibility

C8 tests must include retained aggregate relearning after multiple upstream failure increments, an unknown originator traversing a relay with retained subnet history, first-floor adoption after sequence-state loss, independent host/subnet counters, overlapping prefixes, floor forwarding, malformed/unknown profile markers, authoritative replies and actual member forwarding. C9 adds lowest-address selection, joining delay at both delivery-bound event orders, fail-stop takeover, late lower candidates, withdrawal, sequence-state loss and healing after a declared unsupported loss interval. C10 verifies that real external routes determine export availability, that restored eligibility restarts qualification, and that the external network supplies a return path.

Extension-disabled peers retain the received-subnet profile and cannot establish the extended recovery contract. Mixed scenarios must fail bounded discovery conservatively rather than compare unrelated counters. Candidate messages use their own endpoint and do not alter the standard base message types. New wire behavior, parameters, assumptions and limits belong in user documentation and model evidence. This design supplies a concrete implementation contract; builds, simulations and parent comparisons remain NOT_RUN until the implementing commits execute them.
