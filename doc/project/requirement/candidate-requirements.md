# Candidate requirements

> **Kind:** what · **Status:** current · **Seal:** none · **Owns:** `C-*` · **Stands on:** [accepted-requirements.md](accepted-requirements.md)

Requirements that are **proposed and not yet accepted**. This is the backlog, and it exists so that
[accepted-requirements.md](accepted-requirements.md) can stay short and easy to argue for: nothing
lands there until it is clearly right on its own merit.

A candidate carries a `C-*` identifier. When it is accepted it is **reworded as needed and given an
`R-*` identifier**; the `C-*` identifier is retired and never reused
([DR-ID-FORM](../rule/documentation.md#dr-id-form)). A candidate that is turned down is not deleted:
its row moves to *Turned down*, with the reason, so the same proposal does not return every year.

Candidates are accepted **one at a time**, each reviewed on its own. A batch acceptance is how a
requirement set stops being a set of things anyone actually agreed to.

## How to propose one

1. State it as an **observable capability** — something a user can do, or that INET does for them.
   Not a mechanism: "packets can be captured in a standard trace format" is a requirement, "add a
   pcap writer" is a task.
2. Say **who needs it and for what**. A requirement with no named use is a preference.
3. Check it is not already covered. An accepted requirement stated more narrowly is not a new
   requirement; it is an example of one.
4. Take the next free number, and add a row below.
